Troubleshooting OpenShift 503 errors end to end

OpenShift · Troubleshooting · Networking

A 503 from an OpenShift application is best treated as a traffic-path problem. Instead of changing objects immediately, verify each hop in order: router, Route, Service, EndpointSlice and Pod.

Working principle: prove where traffic stops before making a change.

1. Confirm the Route

Start by checking the hostname, target Service, path and TLS configuration.

oc get route -n my-project
oc describe route my-app -n my-project
oc get route my-app -n my-project -o yaml

If the Route points to the wrong Service or port, the router cannot forward the request correctly.

2. Verify the Service

Check that the Service selector matches the labels on the intended Pods, and confirm port and targetPort.

oc get svc my-app -n my-project -o yaml
oc get pods -n my-project --show-labels

A healthy-looking Service can still have no usable backends if its selector is wrong.

3. Inspect EndpointSlices

EndpointSlices show the backend Pod IPs Kubernetes currently associates with the Service.

oc get endpointslice -n my-project
oc describe endpointslice -n my-project

If there are no endpoints, focus on selectors and Pod readiness before spending time on the router.

4. Check Pod readiness and application listening ports

oc get pods -n my-project
oc describe pod <pod-name> -n my-project
oc logs <pod-name> -n my-project
oc exec <pod-name> -n my-project -- ss -lntp

A Pod can be Running but not Ready. If readiness is false, the endpoint may not be considered available for normal traffic.

5. Test inside the cluster

Before blaming external routing, test the Service from another Pod.

oc run curl-test --rm -it --image=curlimages/curl -- sh
curl -v http://my-app.my-project.svc.cluster.local:8080

If in-cluster Service access fails, the fault is below the Route layer. If it succeeds, move back toward the router.

6. Inspect the OpenShift router

oc get pods -n openshift-ingress
oc logs -n openshift-ingress <router-pod>

Look for backend connection failures, rejected configuration, TLS issues or unavailable endpoints.

A senior-level troubleshooting sequence

  1. Reproduce and record the exact hostname, path and status.
  2. Validate Route target and TLS.
  3. Validate Service selector and ports.
  4. Confirm EndpointSlices contain ready backends.
  5. Confirm Pods are Ready and listening on the expected port.
  6. Test Service connectivity from inside the cluster.
  7. Then inspect router logs and network policy.

This sequence avoids random changes and gives you evidence at every hop.
