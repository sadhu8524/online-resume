How Kubernetes Service traffic actually reaches a Pod

Kubernetes · Networking · Services

One of the most useful Kubernetes networking models is to separate name resolution from packet forwarding. CoreDNS answers the name question. The data plane handles the traffic.

1. The client uses a Service name

A frontend Pod might call backend.default.svc.cluster.local. CoreDNS resolves that name to the Service ClusterIP.

nslookup backend.default.svc.cluster.local

CoreDNS does not proxy the application request. Its job here is name resolution.

2. The packet targets the ClusterIP

The client sends traffic to the Service IP and Service port. The ClusterIP is a virtual service address rather than a Pod interface.

3. EndpointSlices describe eligible backends

The control plane maintains EndpointSlice objects containing backend addresses associated with the Service. These objects give the service data plane the information needed to send traffic toward Pods.

kubectl get svc backend -o wide
kubectl get endpointslice -l kubernetes.io/service-name=backend -o yaml

4. The Service data plane selects a backend

In a kube-proxy based cluster, rules programmed on the nodes implement Service forwarding. The destination is translated from the Service address to a selected Pod IP and target port.

Useful distinction: Service traffic uses the Service data plane. Direct Pod-to-Pod traffic does not need a Kubernetes Service and therefore does not need kube-proxy just to reach the destination Pod IP.

5. DNAT changes the destination

Conceptually, the destination changes like this:

10.96.15.20:80   # Service ClusterIP:port
        ↓ DNAT
10.244.2.17:8080  # selected Pod IP:targetPort

The exact implementation depends on the cluster networking stack, but the mental model remains useful for troubleshooting.

6. The CNI gets the packet to the Pod

Once the destination is a Pod IP, the cluster network handles delivery. Depending on the platform, that can involve routes, overlays, OVS/OVN, eBPF or another CNI-specific mechanism.

7. Return traffic follows connection state

Connection tracking helps the node networking stack maintain the NAT mapping so return traffic belongs to the original connection.

Troubleshooting checklist

  1. Resolve the Service name.
  2. Verify the ClusterIP and Service port.
  3. Check the selector.
  4. Inspect EndpointSlices.
  5. Confirm Pods are Ready.
  6. Confirm the application listens on the target port.
  7. Check NetworkPolicies and the CNI only after the higher-level objects look correct.

This order turns Kubernetes networking from a vague black box into a series of testable hops.
